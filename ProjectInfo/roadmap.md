## 2026-08-22 1553 视频号第一版产品契约与前台边界

决策：無涘 ｜ 记录：Codex

- 视频号处理必须复用现有批量扫描链路，自动点开、取链接并关闭；前台占用不得随视频时长增长，不允许静默退化为完整播放。
- 第一版最终笔记产物定为「原始链接 + 高质量摘要 + 关键要点」；完整逐字稿可作本地临时中间产物，但不默认写入笔记。

理由：用户需要的是可后台批处理、可回看且信息密度高的知识条目，而不是按视频时长占用电脑，或依赖无法复核的第三方摘要。

## 2026-08-22 1642 视频号后台链路定案并通过单卡验收

决策：無涘（授权一次性登录元宝；明确不采用元宝总结，内容由本链路分析） ｜ 记录：Codex

- 元宝独立 profile 只用于把公开 `/sph/` 分享链接解析为腾讯临时凭据；媒体由视频号官方 feed API 获取，元宝不接收逐字稿或摘要任务。
- 媒体下载后由本机 V2T Qwen3-ASR 转写；逐字稿只作临时中间产物。Codex 按固定 JSON Schema 生成高质量摘要和 3–8 条要点，最终笔记写入既有 Obsidian Clippings 目录。
- `collect` 默认在微信扫描结束后继续后台处理视频号；前台 viewer 关闭后用户可立即继续使用电脑。成功任务幂等跳过，失败必须留下阶段与非空错误码。
- 完整视频、WAV 和逐字稿默认在任务结束后删除；manifest 不保存 token、媒体签名 URL 或逐字稿正文。

理由：真实 5 分 28 秒单卡证明该链路无需完整播放即可得到可验证的 601 字摘要与 8 条具体要点；同时满足“不抢电脑”“不信任元宝总结”“不长期保存完整视频”和“失败可辨认”四个约束。

## 2026-08-22 1734 统一采集、按链接类型分流写回 PKM

决策：無涘 ｜ 记录：Codex

- 原有 File Transfer 链路继续负责统一收集链接，不把文章处理与视频处理揉成同一种实现。
- `records[].url` 继续交给既有 `obsidian-web-clipper-ingest`，复用其并发摘要、失败重试与 vault 回读；不得重复实现网页剪藏。
- `video_channels[].url` 交给独立视频后台状态机；只要取得合法 `/sph/`，即可在不占用微信前台的情况下完成媒体解析、本地转写、自有摘要和 PKM 写回。
- 两条分支互不阻塞但必须分别验收；文章 manifest 成功不能代替视频结果，视频成功也不能掩盖文章漏项。

理由：两类内容共享的是“链接采集”和“PKM 目的地”，内容获取机制完全不同。类型路由既保留已成熟的 Web Clipper，又使视频处理独立后台运行，符合不重复造轮子与失败可辨认原则。

## 2026-08-22 1756 统一 Clippings 可移植文件名规范

决策：無涘 ｜ 记录：Codex

- 文章与视频号统一采用 `YYYY-MMDD-主要标题.md`；优先使用内容发布日期，取不到才使用采集日期并明确记录降级来源。
- 文件名采用 OneDrive/Windows 保守白名单：只保留 Unicode 字母、数字、单个 ASCII 空格和半角横杠；其他标点、Emoji 与特殊符号统一换为空格。
- 视频号文件名与笔记标题删除尾部 `#tag`，原始完整标题继续保留在 task 证据中。
- 占位标题不得静默写入；没有可信标题时以 `title_unusable` 失败。重名时按 source 复用或追加稳定 8 位 hash。
- 命名实现由文章 Web Clipper 与视频号写回复用同一共享模块；不改 Auto Note Mover 或目标文件夹逻辑。

理由：Obsidian/macOS 当前能创建某个文件名，不代表 OneDrive、Windows、Office 或未来同步工具都能稳定识别。保守白名单牺牲少量标点，但保留中文主要语义，并显著降低自动改名、路径编码膨胀和跨平台同步失败风险。
