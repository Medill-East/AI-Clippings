> - Think before coding: state assumptions, surface ambiguity and tradeoffs, and ask when the task is unclear.
> - Simplicity first: solve the requested problem with the minimum code; avoid speculative features, abstractions, configurability, or impossible-case handling.

> ## First-Principles and Adversarial Review
> - For product, design, workflow, scoring, visualization, or agent-automation changes, reason from first principles before implementing: define the actual user decision, core entities, axes/semantics, invariants, and failure modes.
> - Use adversarial review before shipping: actively look for confusing representations, wrong ownership, duplicated information, misleading scores, hidden assumptions, stale data, and cases where the system could cause the user to miss a genuinely important opportunity.
> - For visual or information-architecture work, ensure every visual encoding has one clear meaning. Different entity types must not share the same shape unless they are intentionally the same kind of object; labels, lines, positions, colors, and sizes must be explainable.
> - Prefer designs that preserve important-but-not-urgent items while still surfacing urgent windows. Do not let short-term deadlines hide high-fit long-term possibilities, and do not let broad exploratory results masquerade as high-fit opportunities.
> - When implementing agent or automation logic, make the prompt/workflow carry the user's profile and decision criteria into the search itself, then verify the written-back results with invariants and spot checks.
>
> ## Cost-Aware Subagent Allocation
> - Match each subagent's model capability and reasoning effort to the actual task difficulty. Do not default every delegated task to the highest model or effort level.
> - Keep architecture, ambiguous product decisions, adversarial review, cross-source synthesis, and high-stakes judgments with a sufficiently capable lead agent; delegate bounded searches, mechanical extraction, formatting, narrow tests, and isolated implementation work to lower-cost agents when they can meet the same quality bar.
> - Before dispatching, define the subtask, required evidence, expected output, verification method, and the lowest capability tier likely to succeed. Escalate only after concrete failure or newly discovered complexity.
> - Parallelize independent work when useful, but avoid duplicate searches, overlapping ownership, and speculative subagents that do not advance the acceptance criteria.
> - Report material capability limitations honestly. Cost savings must never weaken factual verification, safety, or the user's explicit quality requirements.
